# 欧普 MT428 本地协议研究与证据边界

[English](research.en.md) · [架构设计](architecture.zh-CN.md)

资料整理日期：2026-10-27。对象为 **MT428-D0.5×36+0.2×21-WTT**。本文汇总既有实测记录与公开资料；本次文档整理未连接台灯、发送报文、登录私人账户或重新执行硬件测试。结论限定于已测设备及其当时固件，不代表所有 MT428、HiLink 或欧普产品。

所有示例台灯地址均为 `192.0.2.42`，示例 MAC 均为 `02:00:00:00:00:01`。前者属于 RFC 5737 的 **TEST-NET-1 文档地址段**，后者是人为构造的本地管理单播 MAC；部署时必须分别替换为获授权设备的地址和 MAC，不能直接用于真实设备验证。[N4] 本文不发布真实设备标识、用户网络、云端地址、账户材料或原始报文。`238.238.238.238:5683` 是观察到的协议组播常量，含义见第 6 节，不是示例台灯地址。

## 1. 如何阅读证据

| 标记 | 证据级别 | 能支持的结论与限制 |
| --- | --- | --- |
| T | 实测 | 既有记录中的设备响应、写后回读或受控行为；不是本次重新测试，也不是光学仪器测量。 |
| S | 公开源码 | 可检查的实现、常量和范围；源码支持某项功能不等于本型号已经验证。 |
| O | 官方说明 | 产品功能和官方使用方式；不直接给出 UDP 命令映射。 |
| A | 官方分发 APK 静态分析 | 从指定应用版本提取的 SKU 分支、UI 调用及协议字段事实；APK 不是公开源码，静态路径不证明当前固件接受或执行。 |
| H | 假设／待验证设计 | 需要实验的解释或拟议实现，不作为兼容性承诺。 |

第三方体验文章另标为“公开旁证”：用于确认历史型号和使用线索，不提升为本设备实测或官方结论。早期记录只完成发现与查询，后续记录才完成写控制；下面按后续证据更新能力边界，同时保留未验证项。

## 2. 已知能力与未验证范围

发现回复报告 `CLASS_SKU = 0x50061`、**版本原始字段 `0x210`**。不要将 `0x210` 自行格式化为“2.1.0”或认定为某个正式固件版本。官方型号表同时列出另一款 MT428 前缀产品，因此必须保留完整型号后缀。[H3]

| 能力 | 当前证据 | 结论与限制 |
| --- | --- | --- |
| UDP 单播发现与查询 | T + S | `55001` 上 SEARCH、QUERY 成功；响应类型、请求／响应序号、目标身份与 CRC 均有匹配记录。无需在此路径提供云账户凭据。 |
| 电源 | T + S | 显式开启和关闭成功，并做状态回读；通用电源字段是否同时影响侧灯，尚未单独目视验证。 |
| 主灯亮度 | T + S | 写入及回读成功；协议用一个字节表示 `0–255`，百分比为线性换算，并非与官方 App 滑块或物理照度标定等价。未穷举所有亮度值。 |
| 主灯色温 | T + S + O | 已测请求点包括 `2700 / 4000 / 5000 / 6500 K`；适配范围为 `2700–6500 K`。设备报告值可能与请求有差异，没有验证每一个 Kelvin 或测量实际光谱。[H1] |
| 本地场景预设 | T | 将已适配的电源、亮度、色温组合执行并回读；不等于原厂阅读、书写、电脑或最爱模式。 |
| 进程内关灯定时 | T | 已验证设置、取消及一次 1 分钟到点关灯；由服务进程执行，进程退出或重启即丢失，不是灯内倒计时。 |
| 恢复首次读取状态 | T | 可恢复本次服务首次读取的三个字段；不是原厂备份，也无法恢复未知侧灯、模式或计划。 |
| 独立灯臂／侧灯 | O + A；未实机验证 | 已取得 `0x50061` 专用 App 静态路径、候选写命令与查询偏移；不能据此认定当前固件可控，详见第 3、5 节。 |
| 原厂模式／最爱 | O；本地映射未知 | 官方说明存在这些功能，尚无已验证的本型号本地映射。 |
| 原厂重复计划、倒计时、番茄钟 | O；本地映射未知 | 不用本地场景或进程内定时冒充原厂实现。 |
| 按键指示灯、独立“夜灯” | 公开旁证／未知 | 指示灯设置有同型号第三方线索；独立夜灯功能未由本型号官方说明及本地测试确认。[P2] |
| 断开公网、恢复出厂后的离线配网、其他固件 | 未实测 | 本地命令未使用云凭据，不能据此宣称设备完整生命周期完全离线或更新固件后仍兼容。 |
| 路由器常驻部署、ESP 页面接入、MCP | H | 属于后续架构目标，见对应架构文档；不计入当前硬件验收结果。 |

**关灯调参警告：已测固件关灯时忽略调光。既有兼容流程会执行“开启 → 调整亮度／色温 → 恢复关闭”，期间可能明显亮灯或闪亮。** 最终状态仍是关闭，并不意味着整个操作没有发光。恢复状态、组合控制、场景或自动化只要涉及关灯调参，都需要检查这一影响；恢复关灯也可能因掉线失败，不能承诺无条件恢复。夜间应避免此流程，或在显式接受短暂亮灯后执行。新的接口应提供拒绝临时开灯的策略，并向调用者报告实际执行步骤。

### read-only 与 simulate

- **read-only（只读，默认）**：真实设备路径仅允许定向 SEARCH 和 QUERY，拒绝电源、亮度、色温写入以及可能间接写入的场景、恢复、定时到期动作。它仍会发送查询网络流量，不是被动监听，也不等于离线模拟。只在界面禁用按钮不足以实现只读，限制还必须落实到协议发送层。
- **simulate（模拟）**：使用合成状态和可控故障测试解析、API、队列、定时与关灯兼容流程；不得向台灯、组播组或云服务发送报文。模拟结果必须标明来源，不能记为 T 级硬件证据。
- **实验侧灯门禁**：`--experimental-side-light` 允许试验性解析／能力展示；真实实验写入还必须显式提供 `--allow-write`，缺少任一条件都不得写入。启用解析不等于启用写入，更不表示侧灯已获实机验证。门禁不是当前阶段执行未知写入的授权；今晚禁止此类写入。

以上为公开版的模式与门禁约定；具体启动方式以 README 和该版本测试为准。本文没有重新运行这些模式，也不以历史原型测试数量代替公开项目的测试结果。

## 3. 可复核的 UDP55001 协议摘要

依据原始 `pyoppleio`、legacy 分支及既有实测整理。[S1][S2] 下列偏移均以 **0 为起点**；“body 偏移”指解码后的应用 body，不是整个 UDP 载荷。这里只列命令、字段和算法，不提供原始抓包或可重放的完整报文。

### 命令与有效载荷

| 操作 | 消息类型 | 已知 body 语义 |
| --- | --- | --- |
| SEARCH | `0x02010000` | 定向发现请求，空 body。 |
| SEARCH 回复 | `0x02020000` | 身份、SKU、版本原始字段和通信参数；不是完整灯光状态。 |
| QUERY | `0x030f0000` | 状态请求，空 body。 |
| QUERY 回复 | `0x03100000` | 此设备观察到的 body 长度为 **58 字节**。 |
| POWER | `0x03110000` | 一个字节：`0` 关闭、`1` 开启。 |
| BRIGHTNESS | `0x03130000` | 一个字节的亮度原始值；源码允许 `0–255`。 |
| COLOR_TEMP | `0x031b0000` | 两字节、大端、单位 Kelvin；适配范围 `2700–6500`。 |

**58 字节查询 body 中，当前固件仅三个字段完成实测交叉确认，可作为可靠状态。** 补充 APK 静态证据给出偏移 `52–57` 的候选解释，详见下节；它们不得直接升级为当前固件的可靠状态。其余字节也不得仅凭“发生变化”就标为侧灯、模式、计划、时间或番茄钟状态。

| 查询字段 | body 偏移／切片 | 长度与解释 |
| --- | --- | --- |
| `power` | `1`，即 `[1:2]` | 1 字节，已适配 `0 / 1`。 |
| `brightness` | `2`，即 `[2:3]` | 1 字节，原始值。 |
| `cct` | `7`，即 `[7:9]` | 2 字节，大端设备报告色温。 |

### 封装、发现与校验

公开源码中的固定头长度为 `0x7c`（124 字节）；因此已观察到的 182 字节 QUERY 回复由 124 字节头与 58 字节 body 组成。SEARCH 回复观察到总长 185 字节，不应把两个回复的 body 混用。

| 字段 | 封装头偏移 | 用途 |
| --- | --- | --- |
| 请求序号 | `0x64`，4 字节 | 关联请求。 |
| 响应序号 | `0x68`，4 字节 | 本设备回复可与请求序号匹配。 |
| 消息长度 | `0x6c`，4 字节 | 校验应用消息长度。 |
| 校验字段 | `0x70`，4 字节槽 | 存放 CRC16-XMODEM 结果。 |
| 消息类型 | `0x74`，4 字节 | 区分发现、查询与控制。 |
| body 起点 | `0x7c` | 控制及查询 body 解码的起点。 |

SEARCH body 的已知偏移包括：SKU `0x03`（4 字节）、MAC `0x09`（读取 6 字节）、协议设备标识低位 `0x13`（4 字节）、版本 `0x1b`（4 字节）、IPv4 `0x1f`（4 字节）、UDP 端口 `0x23`（2 字节）。只接受配置中预期设备的回复；这些标识不应出现在公开诊断文件中。逻辑 API 的 `deviceId` 不等于发现报文中的协议设备标识。

源码先构造明文并计算 CRC，再对已初始化设备的 body 做基于 MAC 的 XOR：将 6 字节 MAC 重复并截取为 **20 字节掩码，再按这 20 字节循环**。这不等于无限连续按 6 字节循环。接收时先按已知消息类型解码，将校验字段清零，再对从 `0x64` 开始的应用数据核验 CRC16-XMODEM。CRC 与这种 XOR 均不提供可信身份认证或安全加密。[S2b] 旧库解析代码本身不能代替完整的接收校验；适配器还应验证来源地址／端口、类型、长度、序号及发现身份。

本设备的写入以 QUERY 回读确认，不能把 UDP 已发送当作执行成功。组合控制不是设备端原子事务；应允许报告“部分字段成功”或“结果未知”。其他产品中存在不回显请求序号的实现，不构成对本设备关闭序号校验的理由。[S7]

### SKU 专用灯臂／侧灯候选协议：仅 A 级证据

官方分发 App 的静态分析提供了更具体的候选映射。[A1] `SKUUtil.getDeiveTypeBySku` 将 `0x50061` 映射为 `WifiDesklamp_0061`；`ArmControl` 的“灯臂控制／开关／亮度”UI 调用 `SEND_ARM_OPENCLOSE`、`SEND_ARM_BRIGHT`。发送路径使用 `SEND_SMARTFUNCTION`、消息类型 **`0x03450000`**、本地 UDP55001。以下为协议事实的独立摘要，不是反编译代码或原始报文。

| 候选控制 body 字段 | 偏移／切片 | 静态路径中的含义 |
| --- | --- | --- |
| 产品／模板前缀 | `[0:4]` | 四字节前缀包含本产品 SKU；整个模板长度为 **10 字节**。 |
| arm 开关 | `4` | `0 / 1`；模板中未改开关值为 `2`。 |
| arm 亮度 | `5` | 原始值 `10–255`；模板中未改亮度值为 `0`。 |
| head 开关 | `6` | `0 / 1`；模板中未改开关值为 `2`。 |
| head 亮度 | `7` | 亮度原始值；模板中未改亮度值为 `0`。 |
| head 色温 | `[8:10]` | 两字节大端；模板中未改色温值为 `0`。 |

这里的 `arm`／`head` 是应用内部字段名称；其与实际侧灯／主灯的对应和联动仍需目视差分验证。**`2 / 0 / 0` 是 App 模板中的占位事实；当前固件是否将它们理解为“保持其他字段不变”，尚未验证。** 不应据此直接向真实设备发送“仅改侧灯”的组合控制，也不能推定关灯时侧灯命令的行为与旧三字段相同。

| QUERY body 候选字段 | 十进制偏移／切片 | 证据边界 |
| --- | --- | --- |
| arm 开关 | `52` | APK 静态解析，未在当前固件交叉验证。 |
| arm 亮度 | `53` | 同上。 |
| head 开关 | `54` | 同上，不替代实测 `power@1`。 |
| head 亮度 | `55` | 同上，不替代实测 `brightness@2`。 |
| head 色温 | `[56:58]` | 两字节大端，不替代实测 `cct@[7:9]`。 |

实验解析应单独返回 `side_light` 候选数据，标记 `experimental` 与 `apk_static` 来源；不得悄悄覆盖已验证的三个状态字段。可用静态证据提升研究针对性，但侧灯真机支持仍应标为未验证，真实写入仍受双门禁和阶段禁写约束。

## 5. 官方能力、侧灯缺口与白天实验计划

### 官方说明之间的差异

官方 App 说明列出总开关、主灯亮度、侧灯、阅读／书写／电脑／最爱、计划、倒计时与番茄钟。[H1] 官方实体按键说明给出了不同的场景背景光默认值。[H2] 以下为两篇说明的摘要，不是本地预设参数，也未在本轮目视复测：

| 场景 | 智慧生活 App 说明 [H1] | 实体按键说明 [H2] |
| --- | --- | --- |
| 阅读 | 主灯 `4000 K`、默认亮度 `40%`；侧灯 `40%`，可开关。 | 主光源 `4000 K`、背景光源 `100%`。 |
| 书写／写作 | 主灯 `5000 K`、默认亮度 `40%`；侧灯 `40%`，可开关。 | 主光源 `5000 K`、背景光源 `100%`。 |
| 电脑 | 主灯不亮，侧灯默认 `40%` 且可调。 | 背景光源 `30%`。 |
| 最爱 | 默认 `3000 K`、亮度 `40%`、侧灯开启；支持自定义。 | 该按键说明未列独立最爱键。 |

官方 App 说明的主灯调光范围为 `10–100%`，最爱色温范围为 `2700–6500 K`；这与原始协议字节范围不是同一个尺度。官方称总开关同时控制主灯与侧灯，但本项目已测的是通用电源字段，尚不能据此独立确认其侧灯效果。

官方还说明：原厂计划可设一组并按天重复，断网后当前最近一次定时仍有效；原厂倒计时最长 `23 小时 59 分`，该次断网仍有效，提前关灯不会终止计时；番茄钟包含 `25 分钟`计时、暂停及结束提示。[H1] 这些是官方功能说明，不证明执行逻辑全部存于灯内，更不证明本地适配器已实现其配置接口。

## 6. 组播常量与网络边界

既有观察包含 CoAP `GET /.well-known/core` 发往 **`238.238.238.238:5683`**。这说明存在发现请求，不证明谁响应、谁加入了组、哪些 CoAP 控制资源可用，也不证明通用 CoAP 探测能控制台灯。曾向 UDP5683、5686 单播标准发现请求而没有应用回复；这是该探测在当时未成功，不是排除全部 HiLink 协议的证据。

- IPv4 组播地址属于 `224.0.0.0/4`，表示接收组；`238.238.238.238` 不是台灯自身 IP、设备主机名或云服务器地址。此处保留的是协议观察常量，不是私有网络信息。[N1]
- 接收应用通常选择接口、绑定 UDP 端口并加入组；发送者通常不需要先加入组。IPv4 组成员关系可由 **IGMP** 表达，交换机的 IGMP Snooping 可据此缩小转发范围；未启用相应优化时可能泛洪，Wi-Fi AP 也可能做组播转单播。[N1][N2][N3]
- IPv4 到以太网组播 MAC 的映射保留低 23 位，此组映射为 **`01:00:5e:6e:ee:ee`**。这是协议计算值，不是设备 MAC；多个组可能映射到同一个 MAC，IP 层仍需过滤。[N1]
- **IP TTL 是路由跳数限制，不是秒数。** 本次摘要没有可靠的实测 IP TTL，不编造其值。应用头内名为 `TTL` 的字段也不能当作外层 IPv4 TTL。[S2a]
- `238` 前缀本身不保证链路本地；跨路由转发取决于 TTL、组播路由和策略。普通 NAT、HTTP 代理或一般 VPN 不会自动延伸此发现流量，跨网还会受成员关系、防火墙、AP 隔离及 IGMP 配置限制。

**已验证的本地控制使用目标设备 UDP55001 单播，不依赖这条 UDP5683 组播发现路径。** 指定地址并做身份核验即可采用该路径；跨网络的管理入口应调用靠近设备的适配器，无需为了 HTTP／MCP 接入先延伸组播。单播仍需允许请求及回包，并不等于可以穿过任意隔离网络。
